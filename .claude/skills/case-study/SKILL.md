# ケーススタディ生成スキル

`thinking-framework/` 配下の原則蓄積プロジェクトを1サイクル回す。目的は
「本の概念を知識として説明できる」から「実際の判断に反映される」への橋渡し。

引数（`args`）でユーザーが本や概念を指定していればそれを使う。指定がなければ、
`thinking-framework/principles.md` を読んで既にカバー済みの概念を避けつつ、
まだ扱っていない概念（思考の整理学 / イシューから始めよ / 他にユーザーが挙げた本）
から1つ選ぶ。

## 手順

1. **番号とスラッグを決める**
   `thinking-framework/cases/` の既存ディレクトリを確認し、連番（001, 002, ...）と
   概念を表す短い英語スラッグでディレクトリを作る。

2. **`case.md` を書く**
   - 選んだ概念を実地で試す、具体的で現実的なシナリオを書く。
   - **本の名前・概念名・キーワードは一切出さない**（伏せないと、後で「素の解答」を
     書くエージェントがヒントを得てしまい、実験にならない）。
   - **概念を選ぶ時点で「この概念を正しく適用すると、答えが与えられた構造
     （優先順位・選択肢のカテゴリ・自己申告の制約など）そのものを組み替える
     （reframeする）形になるか」を確認する。** `cases/006-010-batch-note.md`
     で検証した通り、設問の結び方（承認可否かオープンな評価依頼か）は
     副次的な要因に過ぎない。主因は、答えが「標準的な批判的思考チェック
     リスト（サンプルの偏り、一次情報か、網羅性、仮説の有無など）」で
     到達できてしまうかどうか。チェックリストで到達できる概念は、設問を
     工夫しても収束しやすい。

3. **`answer.md` を書く**
   - その概念に基づいた模範解答・分析を書く。
   - 冒頭に `grounding: quote`（ユーザーから実際の本文抜粋が提供された場合）または
     `grounding: paraphrase`（Claude自身の知識による再構成の場合）を明記する。
   - paraphrase の場合は、確信度が低い細部があれば正直にそう書く。
   - ユーザーが会話中に本文の引用を貼ってくれていれば、必ずそれを優先して使う。

4. **素の解答を取る（ブラインド）**
   `Agent` ツールを **`run_in_background: false`** で呼び、以下を守る:
   - プロンプトには `case.md` の本文シナリオ**のみ**を渡す。本の名前、概念名、
     このプロジェクトの目的、`answer.md` の内容は一切含めない。
   - 「これは思考法の実験の一部です」であることは明かして構わないが、
     どの概念を試しているかは明かさない。
   - 出力をそのまま `prediction.md` として保存する。

5. **`diff.md` を書く**
   `prediction.md` と `answer.md` を比較し、ズレを具体的に特定する:
   - どこが一致し、どこが違ったか
   - そのズレは「問い」「穴」「重み」のどのカテゴリか（複数可）
   - なぜそのズレが起きたと考えられるか（一般化しすぎない、この事例固有の分析）

6. **`principles.md` に追記する**
   - 既存のエントリと重複・類似していないか確認する。類似があれば新規追加ではなく
     既存エントリの文言を強化・具体化する。
   - 新規なら以下の形式で追記する:

     ```markdown
     ## [NNN] <短いタイトル> (カテゴリ: 問い|穴|重み)

     **状況**: <ケースの要約、1-2文>

     **誤り**: <素の解答が外した点>

     **原則**: <一般化した教訓、次に同種の場面で思い出せる一文>

     出典: <本のタイトル>（grounding: quote|paraphrase） / ケース: `cases/NNN-slug/`
     ```

7. **ユーザーに報告する**
   何のケースを試し、どんな原則が加わった/強化されたかを2-3文で報告する。
   `principles.md` や `cases/` の全文を貼り付けない。

## 注意

- 複数件まとめて依頼された場合、`case.md`/`answer.md` の執筆（重複チェック
  含む）は1件ずつ順番に行うが、**ブラインド解答を取るAgent呼び出し自体は
  複数件を並列で投げてよい**（各Agentは互いに独立で、文脈も共有しないため
  ブラインド性は損なわれない）。並列化してよいのはこのステップのみで、
  `principles.md`への重複チェック・追記は結果が揃ってから順番に行う。
- `answer.md` を書いた後、絶対に自分の記憶からそれを「知らないふり」をして
  `prediction.md` を書かない。必ず新規の `Agent` 呼び出しで生成すること
  （同一会話内で書くと自己参照になり、実験として無意味になる）。
- 同じ形式のシナリオ（例: 「どう思いますか」型）が3件以上連続で模範解答に
  完全収束した場合、無理に原則をひねり出さず、`cases/`配下にバッチ横断の
  メタ分析ノートを書き、このSKILL.md自体の設計指針を見直すこと
  （`cases/006-010-batch-note.md` を参考例とする）。
