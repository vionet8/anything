# このプロジェクトで得た技術的な知見

three.js + @pixiv/three-vrm でキャラクターに衣装を着せ、写真ゲームを作る過程で
つまずいたポイントと、その対処法のメモ。次にVRMキャラクターを扱うときの参考用。

## 1. 衣装は「塗り直し」ではなく「別ジオメトリ」で作る

モデル本体のTops/Bottomsテクスチャを塗り替える方式は、色は変えられても形は
変えられない。セーラー襟のスクエアな襟や、ブレザーのラペル（襟の折り返し）は
色ではなく形そのものが違うので、塗り直しでは原理的に無理。

対処: `attachToBone()` でボーンにジオメトリを直接ぶら下げる。モデルが立った
状態のワールド座標（メートル単位）で作って、ボーンのローカル座標に変換する
一回限りの変換にすると、数値が「セーラー襟の裾はy=1.19m」のように現実の寸法
そのものになり、読みやすく検証しやすい。

## 2. 身長差のスケーリングは「高さ/1.756」を衣装全体にかける

3人のキャラクターは身長が違う。衣装のビルダー自体は1.756m基準の固定寸法で
作っておき、`attachToBone`側で `scale = 身長/1.756` を掛けてグループ全体を
スケールする。ビルダーの中で個別に半径だけスケールすると、高さは基準のまま
残ってしまい、背の低いキャラだとスカートの裾が8%高い位置に出る、といった
ズレが起きる。

## 3. 同じ半径に重ねたメッシュはZ-fightingする

セーラー襟を「紺→白→紺」の3枚重ねで作っていたら、重なる部分がチカチカ点滅
した（GPUが深度テストで勝者を決められない）。

対処: 3枚を1枚の頂点カラーメッシュに統合する。頂点ごとにcolor属性を持たせて
`MeshStandardMaterial({vertexColors:true})` で描画すれば、自分自身とは
Z-fightingしようがない。fauna.js（鳥モデル）で先に使っていた手法の転用。

## 4. 半球キャップは「肩パッド」に見える

袖の肩側の蓋を `SphereGeometry` の半球で閉じていたら、肩の上に丸いドームが
乗って見え、「ゴリラみたい」と指摘された。半球はどんな半径でも肩の輪郭から
盛り上がって見える。

対処: 平らな `CircleGeometry` の円盤で蓋をする。同じ開口部を、幅を一切足さず
に閉じられる。

## 5. 円柱状パーツは「横から」と「正面から」で見え方がまるで違う

これが一番時間を溶かした。半袖スリーブ（円柱、半径5cm・長さ16cm程度）を、
肘に向けて正しく数学的に狙って取り付けていたのに、正面カメラだと肩から横に
突き出た平たい「翼」に見えた。

原因は向きの間違いではなく比率だった。円柱は横から見ると長さが見え、正面
（≒円柱の軸に近い角度）から見ると太さ（直径）が見える。長さと太さが同じ
オーダー（16cm長・9〜10cm径）だと、正面からの見た目は太さが支配的になり、
平たい塊に見える。

確認の手順:
1. デバッグ用に単色マテリアル（`MeshBasicMaterial`）へ差し替えて他パーツと
   混同しないようにする
2. 向きの数学（ボーン間のローカル座標差から `setFromUnitVectors` で回転を
   求める）を行列を分解して検算する → 数学自体は合っていた
3. `AxesHelper` をパーツに追加して実際の向きを目で確認する
4. 最終確認は「長さだけ変えて再レンダリングし、見た目が比例して縮むか」を
   見る、という実験的なテスト。理屈より効いた

対処: 単純に短くする（0.16m→0.07m）。半径はそのまま、長さだけ幅と同程度に
ならないところまで削ると、正面からでも太さが支配的にならず解決した。

## 6. デバッグ手法として効いたもの

- 頂点カラーの代わりに単色 `MeshBasicMaterial` で特定パーツだけ塗り分けると、
  似た色のパーツ同士（袖とブラウス地など）を混同せずに切り分けられる
- `setAutoFaceForTest(false)` でキャラクターの自動カメラ追従を切らないと、
  「背後から」のつもりのカメラでも顔が写ってしまい、真の背面/側面ビューが
  取れない
- 極端に寄ったズームショット1枚だけで判断しない。ワイド・3/4・真横・
  真後ろの複数アングルを並べて初めて「翼」の正体（袖）が見えた
- 疑わしいコードを一時的に赤単色に差し替えて「本当にそこにあるのか」を
  可視化するのは、座標計算を目で追うより早い

## 7. プロセス面の教訓

- Playwrightのテストスイートが走っている間に、別のヘッドレスChromiumを
  同時起動すると、リソース競合で両方とも壊れる
- テスト実行中に `node server.js` を落とすと、以降の全テストが
  `ERR_CONNECTION_REFUSED` で連鎖的に落ちる。テストランナー自体が
  `playwright.config.js` の `webServer` でサーバーを起動・管理しているので、
  手動で立てたサーバーは事前に必ず止めてから `npx playwright test` を叩く

## ヘッドレスBlender: 確認用のレンダリングにCyclesを使わない

同じシーン・同じ解像度(930x620)を同じヘッドレス環境で実測した値:

| エンジン | 1枚あたり |
|---|---|
| Workbench | 6.6秒 |
| Eevee | 37.7秒 |
| Cycles (samples 220) | 4分(プレビュー) / 11〜13分(本番) |

縁側シーンの制作では、確認したいことの大半が**構図・ポーズ・接地・髪や布が
どこに落ちたか**だった。これらは全部Workbenchの6.6秒で判定がつく。Cyclesが
要るのは最終的な質感と光の確認だけ。

それを知らずに全部Cyclesで回した結果、1回の確認に4分かかるループになり、
「ちょっと動かして見る」が成立しなくなった。反復が高くつくと、1回の試行に
賭ける変更量が大きくなり、失敗したときにどれが原因か切り分けられなくなる。
遅いループは待ち時間だけでなく判断の質も落とす。

**規則: 確認用のレンダリングは既定でWorkbench。Cyclesは最終出力と、質感や
光そのものを見るときだけ。** `configure_render()` に engine を渡せるように
しておき、`--quick` はWorkbenchに落とすのが本来あるべき形だった。

関連して、シーン構築(0.6秒)とキャラ生成は毎回やり直すほど安くはない。
シミュレーション結果を含む状態を `.blend` に保存しておけば、構図やライトの
調整はシミュレーションを払い直さずに済む(スクラッチのテストでは実際にそう
していたのに、本番のループには持ち込まなかった)。
