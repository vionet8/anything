# 実行ルーティン計画

## 実測コスト（ケース001から）

- ブラインド解答役のAgent呼び出し: 約48,000トークン（サブエージェント側、1回限りで
  このセッションのコンテキストには乗らない）
- 私（オーケストレーター）が case.md / answer.md / diff.md を書き、principles.md を
  編集する分: 明確なログは取っていないが、内容量から見て概算 5,000〜15,000トークン
- **1ケースあたり概算 55,000〜65,000トークン**（現行の設計: サブエージェント1回 + 私が
  直接執筆）

ただし、この見積もりには**私自身のコンテキストが会話を重ねるごとに膨らんでいく分**が
含まれていない。これがこのルーティンで一番効く変数（下記「設計上の選択」参照）。

## 設計上の選択: サブエージェント1個構成 vs 3個構成

**現行（1個構成）**: 私がcase.md/answer.mdを直接書き、ブラインド解答だけAgentに
投げる。1ケースあたりの総トークンは少なめだが、**私自身の会話コンテキストに
case/answer/diffの全文が蓄積し続ける**ため、ケース数が増えるほど「私の1ターンあたり
コスト」が右肩上がりになる（過去の全文を毎回運ぶことになるため）。数十件を超えたあたりで
自動要約（compaction）が頻発し、品質・コストの両面で劣化しやすい。

**代替（3個構成、件数を伸ばすなら推奨）**:
1. 「執筆役」Agent — 概念を知った状態でcase.md/answer.mdを自分で書き、ファイルに保存して
   1行で報告する
2. 「解答役」Agent — case.mdの本文だけを渡され、prediction.mdを自分で書いて保存する
3. 「比較役」Agent — case.md/answer.md/prediction.mdを自分で読み、diff.mdと
   principles.mdへの追記案を書く（重複チェックも自分でprinciples.mdを読んで行う）

私（オーケストレーター）は各Agentを起動して1行報告を受け取るだけなので、
**私自身のコンテキストはケース数に対してほぼ横ばい**になる。トレードオフは
1ケースあたりの総トークンが増える（サブエージェント3回分のツール定義オーバーヘッド、
概算150,000トークン前後）こと。

**結論**: 最初の30〜60件（下記バックログ相当）は現行の1個構成で様子を見て、
compactionが頻発し始めたら3個構成に切り替える。今すぐ切り替える必要はない。

## バッチとチェックポイントのルール

1. **1バッチ = 5ケース**。1回の作業セッションでまず1バッチ回す。
2. バッチ終了ごとに:
   - `usage-log.md` に「バッチ番号・実行したケースID・バッチ前後のtotal_tokens残量・
     体感コスト（compactionが起きたか等）」を記録する
   - `git commit && git push` でその時点までの成果を確定する
   - 次のバッチに進むか、ここで一旦区切るかをユーザーに確認する
3. **セッションの残トークンが200万を切ったら**、そのセッションでの新規ケース着手は
   止め、`principles.md` と `backlog.md` の状態を確定してコミットする。続きは
   新しいセッション（フレッシュなコンテキスト）で `backlog.md` を読んで再開する。
   新しいセッションはそれまでの会話の記憶を持たないため、backlog.md /
   principles.md / usage-log.md の3ファイルだけで再開できるようにしておく
   （このルーティン自体がそのための設計）。
4. **実際に利用制限メッセージが出たら**、それは上記の見積もりより優先する絶対的な
   停止信号として扱う。見積もりが外れていた場合は`usage-log.md`に実測を書き足し、
   このファイルの概算値を更新する。

## 打ち切り基準（品質面）

同じ概念について2〜3ケース連続で「principles.mdの既存エントリと実質同じ」という
結果になったら、その概念は打ち止め（バックログ上で「収束」とマークする）。
新しい情報が出なくなった概念を量産しても、トークンを消費するだけで
principles.mdの価値は増えない。

## 現実的な規模感

- 1冊あたり概念候補は30〜40個程度リストアップしておくが、実際に「収束」まで到達する
  のはおそらく半分〜3分の2程度（15〜25件/冊）。
- 2冊（思考の整理学、イシューから始めよ）でまず60〜90ケースを目標にする。
  現行設計なら概算330万〜585万トークン、このセッションの残量（1,500万）内に収まる
  見込みだが、上記の「私のコンテキスト膨張」を考えると保守的に見て
  40〜60ケースあたりで一度区切り、実測を見てから続けるかどうか判断するのが安全。
